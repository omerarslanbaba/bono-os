# Controlled CBS observation v2

This is isolated development. It neither verifies case 93 nor authorizes deployment or a portal action.

## Safety boundary

The explicit popup starts a 60-second session for one tab, frame and document. Session and network event IDs are distinct. Only the two previously observed document-list paths are eligible. A trusted click on an exact, recognized CBS group label supplies an action marker; it proves that click, not file ownership. No guessed DOM selector or endpoint is used. Other clicks, keyboard input, navigation, selected anchor removal/change, target tab closure/deactivation, expiry, ID mismatch, application denial or incomplete capture stop or reject evidence. Unobservable changes that leave the anchor unchanged remain a limitation; the next mismatched request is rejected.

The probe is passive: it wraps requests already made by the portal. Install and arm send no UYAP requests. Request body streams in a Fetch Request object are not read; absent IDs fail closed. Cached expansion may produce no capture; do not retry automatically.

The observation-only bootstrap imports no normal Core DB/jobs/worker/recovery modules. It reads the case table through SQLite readOnly and writes a separate evidence DB. Query claims return 204; normal command/result/download endpoints are unavailable. Source DB, queue and manual pause are unchanged. Normal Core services, WebView2 and Archive APIs are unavailable during this maintenance mode. Normal Core restart later can resume existing startup/recovery behavior; it requires its own reviewed maintenance step.

## Evidence and privacy

Only safe case-number labels, allowlisted group types, structural parent/child edges, primitive types, bounds, method/path/status, timestamps, scoped IDs and an ephemeral HMAC request reference are retained. No scalar response values, arbitrary labels/keys, document contents or authentication headers are retained. Privacy omissions and capture bounds are distinguished. No raw response is logged on failures. Unknown field names collapse to `unknown`; document-ID/download-reference semantics therefore remain unknown. Root HTTP-200 errorCode is evaluated as an application denial. Other undocumented nested errors are not claimed to be understood.

`caseBinding=request_id_matches_user_confirmed_case` means only exact equality with the read-only historical case record after user confirmation. It does not independently prove the selected portal row's unit or every group's ownership. 2026/51962 and instruction groups stay separate and ownership remains unknown. No metadata import is exposed. Discovery contracts remain executable:false; CBS import guard remains fail closed.

## Packaging and rollback

Run `node scripts/build_observation_package.js <explicit-install-root> <new-isolated-output>` to read preimages and generate payload, exact rollback files and SHA-256 manifest v2. It never copies DB/settings/archive or modifies the installation. The maintenance server entry point rejects normal mode before any normal imports. The entire original server is preserved byte-for-byte in rollback; integration uyap.js/db.js are not installed. Normal mode becomes available only after rollback.

The PowerShell package defaults to Verify. Apply/Rollback/Recover require explicit maintenance approval, a readable process inventory showing no BONO desktop/Core or unidentified node process, and an unoccupied Core port. Node reserves the port for the whole operation and uses an exclusive per-root operation lock. Same-directory staging, fsync, SHA-256 and rename replace each file atomically; postimage hashes are checked individually and as a set. Multi-file installation is resumable, not one atomic transaction. Apply and Rollback are idempotent on known images. Unknown images are rejected; explicit Recover with the matching journal quarantines unknown bytes and restores originals, including missing files. Dead operation locks can be recovered only after PID liveness validation. Evidence DB is retained separately. No process, browser reload or main DB migration is started by the installer. ZIP hash covers scripts and manifest too; compare it before executing scripts. No signature/attestation is claimed.

Launch requires explicit Node with node:sqlite, source DB/schema, new evidence DB, installed extension ID and matching file/tool hashes. Child-only environment prevents parent mutation; PowerShell restores pre-existing values and propagates native exit status. Launcher waits for health mode/build/PID readiness, returns failure on early exit or bind error, and keeps a referenced startup timer so a pending fetch cannot silently exit successfully. Enter/EOF requests graceful stop. A canonical source-side observer lease excludes another observer even on a different port. Source DB remains read-only; only the lease sidecar and separate evidence DB are written. After a crash, use `node recover_observation_lease.js <bundle> <target> <source-db>` in separately approved maintenance; alive/unknown owners are never removed. Corrupt/unreadable lock files require manual review, not bypass.

Do not run the normal Core concurrently. Preflight cannot control an independently launched old copy of Core: close the real desktop launcher and verify all relevant processes, then do not reopen it during maintenance. A mismatched Core is rejected before arm. An old extension cannot be assumed passive; it must be replaced/disabled during approved maintenance. Existing content/probe guards fail closed through missing readiness or conflict. Real Chrome extension reload/page preservation is untested; do not automatically reload the portal. Active profile/extension ID/unpacked source path must be confirmed by the user before Apply. Installed disk hashes alone do not prove the Chrome runtime source.
